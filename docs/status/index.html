Divergence from upstream Cemu

Fork point is b8f2cf4 — the last upstream commit merged before the retarget began. Everything below is what happened after it.

Deleted outright

  • The OpenGL and Vulkan/MoltenVK backends, the GLSL shader emitter and glslang. Metal is the only renderer.
  • The x86-64 recompiler backend and all x86 IML machinery, including the only backend peephole pass that existed.
  • x86 SIMD paths in cpu_features, Carbon key codes, the self-updater, and the portability shims that assumed a second architecture or backend.
  • #ifdef ARCH_X86_64 and runtime arch/backend checks. If something looks like it needs one, it does not.

Rewritten for this hardware

  • cpu_features for arm64; title and content decryption onto the ARMv8 AES extensions, validated against FIPS-197 by a standalone probe.
  • FSpinlock is now os_unfair_lock — a raw spin on an asymmetric-core CPU can burn a P-core against a descheduled E-core holder.
  • Thread QoS with a P/E split. Guest cores and the GPU command thread USER_INTERACTIVE; compile pools sized against the efficiency cluster instead of hardware_concurrency(), which was spawning 17 threads on a 4P+4E machine.
  • Audio onto a lock-free SPSC ring — the mixer had been taking a mutex on CoreAudio's realtime thread.
  • MemMapper for 16 KB pages, screensaver inhibition through NSProcessInfo, and SDL input off a 5 ms main-thread timer.

Added

  • A telemetry harness compiled into the core — counters across GPU, CPU, memory and accuracy, __thread-local and cache-line striped, gated on one branch so a disabled build measurably costs nothing.
  • A golden-scene capture harness (testing/capture-scene.sh) and a scripted BotW driver that reaches a repeatable scene with no human and no save file.
  • A code-anchored Wii U hardware reference — ten documents in docs/hardware/, written against the emulator's own source rather than wiki lore. Writing it found two bugs.
  • A native GameController.framework input provider, crash diagnostics (sigaltstack, arm64 PC recovery, demangled backtraces), CMake-driven bundle signing, and standalone probes in tools/probes/.

Bugs the port surfaced

  • 248 bytes of heap corruption on every startup — the Metal renderer initialised a [3][31] array with a loop bound of 4. It was the real cause of a long-standing // HACK: ... garbage data workaround.
  • MemMapper rounded a mapping's base but not its length and did no rounding at all on unmap, so releasing a guest range failed silently and left it writable across a title switch. 16 KB pages make this reachable where 4 KB pages hid it.
  • The AArch64 backend left the emitter cursor short of the end of generated code, so readyRE() invalidated only part of the I-cache — a stale-instruction hazard on cold paths only.
  • Graphic packs corrupting GPU registers; sampler LOD bias never applied at all; an MTLEvent value wrap that silently disabled command-buffer serialisation every ~29 s; a missing NSHighResolutionCapable handing Metal a half-resolution drawable.

First CPU conformance result — and the recompiler is not the problem

cpu

ppc750cl.s — 23,502 lines of public-domain PowerPC assembly validated by its author against real Espresso silicon — now runs as Wii U homebrew. 1,030 failures, and the recompiler and interpreter arms are identical: zero unique to either. 676 are FPSCR state bits the emulator does not maintain; 354 are wrong values, of which only 3 are integer.

52,330 free HLE calls per frame, and where the context switches come from

Decompose the frame: the open world is not GPU-bound, it is vsync-quantised

Measurement traps

Ways this project has already produced confident, wrong numbers.

A BotW telemetry run is two workloads, and the split is ~50/50

~4,050 frames of menu at 113 draws and 33.27 ms, then ~4,750 of gameplay at 3,516 draws and 49.90 ms. --skip=60 removes none of it. A whole-file median describes no frame that occurred, and because two runs never have the same ratio, that difference reads as a treatment effect. It manufactured a confident −6.2%. Always pass --phase=<gameplay>.

MK8's attract mode is not a fixed workload

It cycles demo scenes with very different draw loads, so two traces taken minutes apart are not comparable and neither are their sample counts. A first A/B read as "4.4× faster" from sample counts; the real figure was 1.77×. To compare implementations, put a runtime toggle behind an env var, flip it every ~20 s inside one process, discard windows that straddle a switch, and report the median of n≥5 per variant.

xcprof compare reports share of CPU, not absolute CPU

If total CPU drops, everything that survives looks like a regression — it reported 15 of them for a change that cut CPU nearly in half. Use it to see *which* frames left the profile; use absolute process cputime over a fixed wall-clock window for the magnitude. Prefer ps -o cputime= deltas over %cpu, which is a decaying average.

Do not divide BotW's GPU time by 16.67 ms

BotW targets 30 FPS, so the budget is 33.3 ms. An earlier revision divided by the 60 FPS budget and concluded the GPU was at "108–147% of budget" and "is what caps the frame rate" — both wrong. At ~50% duty cycle it is not the limiter in this scene, and cutting GPU time 16% moved the frame rate not at all.

cemuLog_log does not write to stdout

It writes to ~/Library/Application Support/TesseraEmu/log.txt. Grepping the process's redirected stdout for errors — or for your own instrumentation — silently finds nothing and reads as "clean". Use --verbose. And CemuApp::OnExit calls _Exit(), so kill -9 loses buffered log and shader-cache writes.

Scripted edits fail silently

Source uses tabs; a heredoc written with spaces will no-op a Python str.replace and report success. Worse, an anchor that is not unique attaches your counter to the wrong call site — that happened, and put a counter on the *temporary* render-pass path, reading 2–4 passes/frame instead of 202. It was caught by arithmetic, not by review. Prefer explicit line ranges and always git diff --stat before building.

An in-process scope timer cannot measure a fiber switch

Fiber::Switch does not return until the fiber is resumed, so the timer measures descheduled time. It reported 197 ms of "busy" inside a 49.9 ms frame. A microbenchmark is the right instrument.

A pixel diff of the MK8 title screen proves nothing

The "Press A to start" prompt pulses and the background animates, so ~22% of pixels differ between any two captures. Use targeted instrumentation to show a rendering change is live. Relatedly, capture-scene.sh uses screencapture -R, which grabs a screen *region* — raise the window first or you capture whatever is on top of it.

GPU-time counters soak: the same frame costs 5% more GPU after four minutes

Across the Korok gameplay phase, sliced into sixths, draws (3,472→3,518), render passes (202), attachment bytes (800 MB) and CPU core-busy (9.4–9.5 ms) are all flat, while gpu.busy_ns climbs 16.9→17.8 ms and gpu.readback_forcefinish_ns climbs 6.5→7.5 ms — identical work, more GPU time, reproduced in all three runs. So the *median* of those counters is a function of how long you recorded and where in the run you sampled, and two arms of an A/B must be equal-length and equally-positioned or the longer one loses. Frame time, fps and frame_critical_path_ns do not drift at all (0.0%) because they are vsync-pinned, which is why this hides. It also explains the recorded 16.45 ms against today's 17.12–17.15, and retroactively explains the "±2% swing between identical runs" noted for the drain counter — that was not noise, it was window placement.

The build hash in every telemetry header is captured at cmake *configure* time

CMakeLists.txt:15 runs git log --format=%h -1 inside execute_process and bakes the result into -DEMULATOR_HASH, which only re-evaluates when cmake reconfigures. A binary built from cebe17f reported build 064d9a7 — eight commits stale — in its window title and in the build field of every --telemetry run header. testing/capture-scene.sh has the mirror-image problem: it stamps baseline.tsv with the *repo's* git rev-parse HEAD, which says nothing about what the binary was built from. Neither surface proves provenance; run cmake -S . -B build … before a measurement that will be quoted. The hash reaches everything through precompiled.h, so refreshing it costs a full rebuild.

A counter reading zero is not evidence until you check it has an increment site

Sweeping all 113 TLM_COUNTER declarations against src/ found 14 that nothing ever writes: gpu.pipelines_compiled, acc.render_self_dependency, and **all twelve mem.***. The mem.* block covers buffer-cache scans and uploads, texture-cache reloads and shader-cache hit/miss — precisely the subsystem behind the largest graphics finding on file, that UploadToBufferCache fires ~25/frame and breaks render passes. That finding had to be established by backtrace attribution at every pass teardown because these counters do not work. The instrumentation for the question was sitting in the file reading zero, and zero was indistinguishable from "not wired". Check the hook exists, and prefer a positive control in the same code path — gpu.depth_sampled_draws reads 392/frame beside the self-dependency detector for exactly this reason.

The instrument only sees the scene you point it at

A confirmed out-of-bounds write — geometry-shader texture bindings landing past the end of MetalState::m_textures and into the next member — survived in a fork this heavily measured because gpu.draws_mesh is 0 in BotW Korok, the only scene anyone measures. Absence of a signal in the benchmark is not absence of the bug, and a scene chosen for being *exactly repeatable* is by construction a narrow one. Where a defect is structural rather than statistical, prove it with a static_assert and stop waiting for a run to show it.

An update and DLC in mlc01 do not make a title bootable

~/Library/Application Support/TesseraEmu/mlc01/usr/title/ held 0005000e/101c9400 (BotW update, 3.0 GB, containing U-King.rpx) and 0005000c/101c9400 (DLC, 2.0 GB) — 5 GB of convincing-looking content with an executable in it. The base title is 00050000/… and lives in Roms/ as a disc image; an update carries only changed files, so with Roms/ emptied nothing boots. Worth checking before planning any work whose verification is a run: the presence of U-King.rpx is not the presence of a game.

A toolchain can be blocked two independent ways at once

Building Wii U homebrew here needed devkitPPC, and the two obvious routes were both closed: the installer needs sudo, which cannot be answered when driving this repo remotely (and the agent shell has no TTY, so sudo's credential cache cannot carry across either), while downloads.devkitpro.org returns 403 via Cloudflare — including its root, though github.com and cloudflare.com return 200, so it is site-specific. Critically that host serves every source devkitPro's buildscripts fetch, binutils/gcc/newlib included, not just their own components. The way through was that their download loop skips files that already exist and honours BUILD_DKPRO_SRCDIR, so pre-staging all six archives from GNU/sourceware/GitHub made the stock scripts work. Two genuine bugs in those scripts surfaced on the way: a three-argument call to a four-argument function in the mn10200 step, and no --with-system-zlib, whose bundled zlib defines fdopen to NULL and breaks the macOS SDK's stdio.h. All recorded in docs/testing/00-test-strategy.md §4.

A homebrew sample reading zero frames is usually its own asset path, not the emulator

wut's gx2_triangle booted cleanly, issued two command buffers and rendered zero frames, which reads exactly like a renderer defect. It is not. The sample loads its shader from the SD card — WHBGetSdCardMountPath(), backed by <userdata>/sdcard/ — and not from the .wuhb bundle's /vol/content, so WHBReadWholeFile returned NULL and it goto exited before the render loop. Two compounding reasons it stayed invisible: the sample reports the failure through WHBLogUdpInit (UDP, port 4405) rather than OSReport, so --forward-console-logging showed nothing at all; and a title that exits early looks identical to one that renders nothing. wut-tools ships udplogserver to receive that stream. Check a sample's own I/O and logging transport before suspecting the renderer, and prefer WHBLogCafeInit in ROMs we write so the standard flag works.

The graphics-test toolchain is three separate installs, and two of them are optional-looking but are not

Building a Wii U test ROM needs devkitPPC (compiler), wut-tools (host utilities: elf2rpl, rplimportgen, wuhbtool) and wut (the library) — three separate builds. Missing wut-tools fails deep inside wut's build with rplimportgen: No such file or directory rather than anything resembling "a tool is missing". wuhbtool additionally needs libfreeimage, whose absence fails at *configure* time with 'libfreeimage' not found and takes the whole tools build with it. And graphics tests additionally need CafeGLSL's glslcompiler.rpl in cafeLibs/ — without it a ROM builds fine and reports glslcompiler.rpl-not-found at runtime. testing/toolchain/build-devkitppc.sh does all of it; testing/toolchain/README.md explains why each piece is there.
